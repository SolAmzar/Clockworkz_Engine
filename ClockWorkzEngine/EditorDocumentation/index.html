Editor Architecture Documentation

A comprehensive guide to the ClockWorkz Engine editor workflow, state management, and undo/redo architecture.

Overview & Architecture

The ClockWorkz Engine Editor operates on a robust state machine built on top of GameState. The editor splits responsibilities between launching projects (Hub), managing game scenes (Editor State), and testing them (Play State).

Transitions between these states manage the setup and teardown of ImGui panels, rendering configurations, and engine subsystems.

Editor Hub State

The EditorHubState acts as a Unity-style project launcher. It is the initial entry point when the engine starts in editor mode. Its primary responsibilities include listing recent projects, creating new projects, and resolving scene paths.

Key Data Structure

Projects are managed using the ProjectEntry struct, saving metadata necessary to bootstrap the engine into the correct project context.

struct ProjectEntry {
    std::string name;
    std::string path;         // Project root relative to SourceRoot
    std::string initialScene; // Initial scene path
    std::string description;
};

Behind the scenes, the hub manages threaded background building via CMake, preventing the UI from stalling during heavy compilation steps.

Level & Scene Editor

The core editing experience resides in EditorState and LevelEditor. This state hooks deeply into the ECS (Entity Component System) to provide visual tools for manipulating Entities.

Features & Capabilities

  • Integrated Gizmo System: Translate, scale, and rotate entities seamlessly in the viewport with grid-snapping support.
  • Prefab Management: Drag-and-drop workflow for saving and loading complex entity configurations via JSON.
  • Tilemap Painting: Specialized tools for painting grid-aligned sprites across multiple layers.

Editor State Initialization

When entering the editor, all engine subsystems pause gameplay logic while rendering loops remain active. Notice how entities are tracked selectively via IDs to prevent dangling pointers:

Entity Snapshotting

For complex changes (e.g., inspector edits where multiple properties change at once), the engine takes a full snapshot of the entity's components using EntitySnapshot.

struct EntitySnapshot {
    std::string tagName{"Entity"};
    Components::Transform transform{};
    bool hasSpriteRenderer{false};  
    Components::SpriteRenderer spriteRenderer{};
    // Flags and data for ALL core components...

    static EntitySnapshot capture(ECS::World& world, ECS::Entity entity);
    void restoreInPlace(ECS::World& world, ECS::Entity entity) const;
};

Command Implementation Example

A specialized command to modify components takes the before and after states to ensure precision:

template<typename T>
struct ModifyComponentCmd final : IEditorCommand {
    ECS::World& world;
    ECS::Entity entity;
    T before{};
    T after{};

    void execute() override { 
        if (auto* c = world.getComponent<T>(entity)) *c = after; 
    }
    void undo() override { 
        if (auto* c = world.getComponent<T>(entity)) *c = before; 
    }
};

Using templates allows the engine to create strongly-typed commands for any ECS component on the fly without writing custom logic for every struct.

Sprite & Animation Editor

The SpriteEditorState is a dedicated state for isolating texture and animation creation from the dense level editor context. It constructs a virtual grid overlay to slice textures into animation frames and instantly previews the output.

class SpriteEditorState final : public GameState {
private:
    // Slicing Tool Variables
    int m_sheetWidth{512};
    int m_sheetHeight{512};
    int m_cellWidth{64};
    int m_cellHeight{64};
    
    // Playback Variables
    int m_startFrame{0};
    int m_endFrame{0};
    bool m_playLoop{true};
};
